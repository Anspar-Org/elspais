# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Also read**: `AGENT_DESIGN_PRINCIPLES.md` for architectural directives and mandatory practices, and `AGENT-ONBOARDING.md` for how to drive the tool itself — which surface answers which question, and the MCP tool for each task.

## Overview

elspais is a minimal-dependency Python requirements validation and traceability tool. It validates requirement formats, checks hierarchy relationships, generates traceability matrices, and supports multi-repository requirement management with configurable ID patterns.

## Full documentation

Full specifications are contained in spec/ and docs/. Don't read more than is necessary for the task.

**IMPORTANT**: there is only ONE main graph data struct. there is only _ONE_ modular system for CRUD opertions.
**IMPORTANT**: **DO NOT** change the structure of Graph or TraceGraph or GraphBuilder. Do not violate the current encapsulation.
**No Duplicate Library Functions**: Do NOT create duplicate implementations of core functionality across modules:
- Hierarchy traversal: only in TraceGraph (roots, children, parents, find_by_id)
- Coverage calculation: only in GraphBuilder (computed during build)
- Requirement loading: only in core/loader.py (create_parser, parse_requirements_from_directories)
- Git state detection: only in core/git.py (get_git_changes, GitChangeInfo)
- Identifier pattern derivation: only in `utilities/patterns.py` (`IdResolver`, `build_resolver`, `component_regex`). Parser-level regexes shared across modules live in `graph/parsers/patterns.py`. There is ONE authority for the whole identifier grammar — canonical pattern, component sub-pattern, assertion label, the component-to-label boundary, and multi-assertion expansion — reachable through its public interface. Do NOT compose an identifier regex anywhere else, and do NOT reach for a private helper to get one. Matching admits case and digit-padding variation in any part of an identifier — component and _Assertion_ label alike — so a spelling differing only in case or padding still resolves; it admits NOTHING else (REQ-d00212-S), so a boundary spelled with another character is a reference spelled wrongly rather than a second notation, and is reported rather than repaired; rendering always emits the one canonical spelling, and a non-canonical-but-admitted spelling is reported as a style finding (`references.identifier_form`) rather than refused. A configuration holding two elements that differ only in case is rejected at validation time, since matching cannot then tell them apart.
- Federation membership: only `plan_federation()` in `graph/federation_plan.py`. It walks associate declarations depth-first from the invoking repo, so a repository the root never names directly still joins the federation (REQ-d00202-D). Members are identified by the namespace their declaration names (REQ-d00202-G), so one namespace reached again at the SAME directory is a diamond converging to one entry, reached again at a DIFFERENT directory is the collision `NamespaceConflict` reports (K), and reached again up the current declaration chain is a cycle naming that chain. Git origin decides nothing; it is carried on `PlannedRepo`/`RepoEntry` as data the viewer reports. Surfaces holding a built graph read `FederatedGraph.iter_repos()`; surfaces holding only config call `plan_federation()`. Do NOT re-derive membership from the root's `[associates]` table — that answer is a strict subset of the federation. The planner is also the ONE authority on what enters a federation, for every surface that asks — a build and `elspais associate` alike, so a declaration is recorded exactly when a build would admit it (REQ-d00289-E+H). It is where identity is enforced, before any graph exists: no two directories may claim one namespace (REQ-d00202-K), a declaration's namespace must match the one the repository at that path declares (L), and a declaration must carry both a path and a namespace (B) — `get_associates_config()` refuses one that does not, and the planner reports it as a `FederationError` naming the declaring repository. There is no `[associates] paths = [...]` array; a bare path names no namespace and so cannot say which repository it means. Because one namespace names one member, code MUST NOT ask whether some other repo also claims a namespace — that question now has one answer.
- Cross-repository identifier reading: only `FederatedIdReader` in `utilities/patterns.py`. It alternates each member's own `IdResolver.grammar()` fragments (never merges configs, per REQ-d00251-L) and normalizes an extracted reference under the grammar of the member that claims it. `build_graph()` resolves the membership from `plan_federation()` BEFORE any file is scanned and hands the member resolvers to the code/test `FileDispatcher`, so an identifier owned by any member is recognised in every member's code and test annotations (REQ-d00269-C). The spec grammar stays narrow — a repository declares only identifiers it owns. Over a single repository the reader emits that repository's fragments verbatim, so a lone build is byte-identical. Do NOT hand-roll a per-member probe loop.
- Citation form: ONE form declares a relationship in a code or test file — a _Traceability_ keyword, its colon, and the reference list it introduces, as the first content of a comment opened by that file's own marker (continued onto the next eligible line only where the list ends with `REF_LIST_SEPARATOR`, REQ-d00269-H). Nothing else declares one (REQ-d00269-L): a test function's NAME references nothing however it is spelled, and there is no block-header form gathering indented identifiers beneath a keyword line. An identifier opening a comment that no keyword introduces is recognised only so it can be reported as an undeclared relationship (REQ-d00272-O) — do NOT add a second way to read a citation.
- Reference-list reading: only `FederatedIdReader.parse_ref_list()`. It is the ONE place a list of references is divided into its items, and it matches each item whole against the same grammar that reads a lone identifier — so a list never admits a spelling a single reference would not. Composition is the mirror of this: `IdResolver.make_assertion_id`/`make_assertion_ref` are the only places an identifier is spelled, and a caller without a grammar raises `GrammarUnavailable` rather than assuming `-`/`+`. Each item of the list is judged on its own: a well-formed item produces its reference whatever its neighbours read as, and an item is still matched whole, so a reference is never resolved by an identifier found inside a larger one. An item the grammar does not account for is returned carrying the fault class it reached, so the caller reports it rather than losing it. Do NOT `split(",")` a reference list anywhere. The dividing character is `REF_LIST_SEPARATOR`, and REQ-d00251-M bars either assertion separator from also being it — a list is split before its items are read, so a collision shreds every multi-assertion reference silently.
- Severity resolution: only in `utilities/findings.py`. ONE vocabulary (`off`, `info`, `warning`, `error`, fixed by the schema per REQ-d00212-U and refused at config-read time per REQ-d00212-V) and ONE authority, `severity_for(check_name, config)`, which every health and doctor check calls. `REGISTRY` records for each check its category, the severity it carries unconfigured, and the ONE configuration path it reads — a named legacy setting (`[rules.references]`, `[rules.format] no_assertions_severity`/`no_traceability_severity`, `[rules.coverage] uncredited_evidence`/`external_test_failure`, `[terms.severity]`) OR an entry in the general `[rules.severity]` table keyed by check name, never both, so a project that sets the setting it read about always sees it take effect (REQ-d00285-D/E). `off` means the condition is not reported here: the check returns `skipped_check()` — passed, `info`, no findings, and a message saying what was withheld (REQ-d00285-G). `ok` is RETIRED as a value. `HealthCheck` refuses to be constructed carrying anything outside `REPORTED_SEVERITIES`, which is what makes a severity counted nowhere impossible. Do NOT read a severity out of the config at a call site, and do NOT hardcode one.
- Report input derivation: only `report_inputs_from_args` / `report_inputs_from_params` in `commands/_edges.py`. A `--scope` name is expanded against config at the edge that was invoked and NOWHERE else — a compute path handed a raw declaration cannot tell a project's words from a reader's, and REQ-d00280-D turns on exactly that difference. `compute_*` functions take a frozen request from `commands/_requests.py` holding final values and resolve nothing; `dict[str, str]` is an HTTP wire format, never an input to a command. Do NOT write a function taking `args_or_params`.
- Configuration declaration nodes: only in `graph/declarations.py`. It is the ONE authority for which configuration tables are held as nodes (`DECLARED_TABLES`), how a declaration node is built, how its text is taken for a version, and how one is addressed by name. Do NOT walk a held `TOMLDocument` for a declaration at a call site, and do NOT spell a `decl:` id anywhere else.
- Hash computation: only in `utilities/hasher.py` (`compute_normalized_hash`, `calculate_hash`). Do NOT create alternative hash functions elsewhere.
- Term scanning: only in `graph/term_scanner.py` (comment extraction, term reference classification, markup analysis). Uses `ast.parse()` for Python files, regex for others.
- New-spec-file path validation: only in `utilities/spec_paths.py` (`validate_new_spec_path`) — shared by the viewer HTTP route and the MCP move tool so both surfaces accept and reject identically.
- Coverage aggregation: only in `graph/aggregation.py` (`aggregate_by_level`, `tier_buckets`). CLI `summary`, MCP `get_project_summary`, and the viewer all read this one module so identical questions get identical answers — do NOT recompute level/tier rollups elsewhere.
- Version-token derivation: only `node_version()` in `graph/render.py` (digest primitive `compute_version_hash()` in `utilities/hasher.py`). Do NOT derive concurrency versions elsewhere.
- Concurrency guards: ONE helper pair — `_guard_version()` / `_guard_mutation_tip()` in `mcp/server.py` — shared by the MCP tools and the viewer HTTP routes (`server/routes_api.py` delegates to them). Do NOT reimplement the checks or hand-roll rejection bodies.
- Rebuild-and-publish: only `rebuild_shared_graph()` in `mcp/shared_state.py`. It re-reads config from disk, publishes config → graph → `build_time` under the holder's `write_lock`, then runs the holder's `post_rebuild_hooks`. Every reload surface reaches it — `AppState._rebuild()` (so the freshness middleware), `/api/reload`, `/api/revert`, MCP `refresh_graph`, and every surface that rebuilds after writing spec files: the viewer's `/api/save`, MCP `save_mutations`, and the MCP tools that write a file directly. Change-detection state living outside the holder registers a hook instead of being refreshed per caller — `AppState` registers both `snapshot_mtimes` and the `daemon.json` `config_hash` sync — so a rebuild reached through any surface leaves identical state behind it (REQ-p00004-O). Registration is also what scopes those effects: a stdio MCP server holds a private graph, registers nothing, and so never stamps freshness records belonging to a daemon in the same repo. A hook that raises is warned about, not allowed to retract a swap readers already see. A config that will not parse — or a build that fails for any other reason — publishes nothing and is reported as a failure naming the cause, with the previous graph left live; it never raises out of a caller that has already written its files. A surface that wrote files before rebuilding reports that failure beside its successful write as `rebuild_error` (`_rebuild_after_write` in `mcp/server.py`, and `/api/save` identically), and the viewer raises the stale banner carrying it. Do NOT hand-roll a rebuild-and-swap.
- Report export rendering: only `export_document()` / `markdown_to_pdf()` in `server/export.py`, which renders NOTHING of its own — a markdown or CSV export is the command's formatter over the command's payload (`render_summary`, `render_trace`, `render_gaps`, `render_checks`, each the ONE rendering its `run` also prints through -- `trace.run` prints `render_trace` and composes no table of its own), and a PDF is that markdown put through `render_pdf()` in `pdf/renderer.py` — the ONE pandoc invocation, the same template `elspais pdf` typesets with; do NOT call pandoc anywhere else. What a report offers is read off `commands/report.py`'s `FORMAT_SUPPORT`, never declared again. The export route reads its query with the SAME module-level `*_request_from_params` builder the matching `/api/run/{report}` route reads with (REQ-d00298-C), so the page's request-building lives in exactly one place per report. Do NOT add a second renderer or a second query reader for a report.
- Daemon address reservation: only `reserved_port()` / `reserve_port()` in `mcp/daemon.py`, recorded in `.elspais/daemon-port.json`. Kept DELIBERATELY separate from `.elspais/daemon.json`: that record names the process serving a tree now and is deleted when none is (REQ-o00076-E), while the address must outlive having nothing to serve (REQ-o00076-K) so a client that resolved it once still reaches the replacement. `start_daemon` asks for the reservation; `run_server` falls back to a free port and warns if it is occupied (REQ-o00075-G — an occupied port never stops the tool working), and whatever was actually bound is re-recorded. Do NOT put the port in `daemon.json` or derive it from the path.
- Serving-process staleness: only `serving_difference()` in `mcp/daemon.py`, which compares recorded version, recorded `executable_hash` and `config_hash` against the client asking. Both `ensure_daemon()` and `_engine._try_daemon()` read it and follow one policy: a daemon that differs is replaced UNLESS it holds unsaved work, in which case it is left alone and the client is told (`notify_serving_difference()`, REQ-o00076-J) — those changes exist nowhere else, and answers from an older program are recoverable where they are not. The dirty probe is `daemon_has_unsaved_work()`, which reads `get_daemon_mutation_count()`. Do NOT re-derive staleness or re-probe `/api/dirty` at a call site. `executable_hash` is written once at startup and never refreshed, because what a process is running cannot change while it runs.
- Installed-program identity: only in `mcp/executable.py` (`compute_executable_hash`, `ExecutableWatcher`, `installation_can_change`, the process-scoped `watcher()`/`difference()`). Watching happens ONLY where `installation_can_change()` — an editable install, the one case where the program moves under a running process; a fixed install pays nothing. A daemon that finds its program superseded RENEWS itself (`renew_for_installed_program` in `mcp/server.py`: persist what is held, then `os.execv` to rebind the same reserved address, REQ-o00077-D) rather than stopping — held work is carried across, never a reason to refuse. Only a process that cannot renew without ending its client's session (stdio) refuses, via `_guard_executable_drift` (REQ-o00077-F). This is the program elspais is RUNNING, and it is deliberately kept apart from the content elspais TRACES — the word `code` is never used for it, because in this estate `code` already means the source files being traced (`NodeKind.CODE`, `code_tested`, `code:` ids). Content going stale is answered by rebuilding the graph; a program that has moved cannot be answered that way at all, so the two conditions are never merged into one flag or one report. `daemon.json`'s `config_hash` answers a third question again (the tool's configuration) and stays in `mcp/daemon.py`.
- Viewer URL prefix: only `create_app(state, base_path=...)` in `server/app.py` mounts the route table, and `validate_base_path()` there is the ONE authority on the accepted form (empty, or one or more segments of ASCII letters and digits, `-`, `_`, `.` and `~`, each introduced by a single `/`, no segment being `.` or `..`). The page reads it as the Jinja variable `url_prefix` and the JS global `URL_PREFIX`; `apiFetch()` prepends it to every root-relative request, so callers pass `/api/...` and NEVER a prefixed URL. The Jinja variable `base_path` already means the REPOSITORY ROOT — do NOT reuse it for the prefix. Middleware matching a path by string is handed the prefix rather than reading it off the scope. The record a server leaves in `.elspais/daemon.json` carries the prefix as `base_path`, and `daemon_url(info, endpoint)` in `mcp/daemon.py` is the ONE place that record becomes an address — every reader (the CLI's `_daemon_client`, `doctor`, `mcp env`, the viewer's port-conflict probe) builds its URL there. Do NOT spell `http://127.0.0.1:{port}` anywhere else: at the root of its port a prefixed server answers nothing. The page's state cookie is scoped to `URL_PREFIX` (REQ-d00295-F).
- Do NOT create hierarchy.py files in multiple locations

**No Backwards Compatibility**: backwards compatibility is NOT a goal of this project. Do not add a migration that silently rewrites an out-of-date input, an alias that keeps a former name working, or a branch that accepts a shape the tool no longer emits. Where an input is no longer admitted, REFUSE it with a message naming what to change -- `_legacy_style_message` in `config/schema.py` is the quality bar. A refusal is not a compatibility shim; keep those. This licence is narrow in one direction only: before removing anything, establish what it was for, because a shim that turns out to serve a live purpose is not back-compat.

**Minimal Dependencies**: Core requires `tomlkit` (pure Python TOML library), `pydantic>=2.0` (config schema validation), and `tyro>=0.9` (CLI generation). Uses Python 3.10+ stdlib for everything else.
**Hierarchy Rules**: Requirements have levels defined in `[levels]` (e.g., prd rank=1, ops rank=2, dev rank=3). Each level declares its `implements` list (e.g., `dev.implements = ["dev", "ops", "prd"]`).
**Hash-Based Change Detection**: Body content is hashed (SHA-256, 8 chars) for tracking requirement changes. Centralized in `utilities/hasher.py`.
**Configuration System** (`config/__init__.py`, `config/schema.py`) almost all parsible content is configurable. `load_config()` returns a plain `dict[str, Any]`; defaults come from the `ElspaisConfig` Pydantic model via `config_defaults()`. Config version is 5. Top-level fields: `project`, `levels`, `id_patterns` (alias `id-patterns`), `scanning`, `rules`, `keywords`, `validation`, `changelog`, `output`, `associates`, `terms`. There is no `ConfigLoader` class or `DEFAULT_CONFIG` dict. There are THREE layers and the environment is not one of them: the schema's defaults, `.elspais.toml`, then `.elspais.local.toml` over it. Deriving a configuration from documents is ONE function, `derive_config(documents)` -- a PURE function of documents already parsed, holding the deep merge, the `[levels]` replace-don't-merge rule, the version and legacy-setting refusals, and the schema validation. `load_config()` reads the documents `config_document_paths()` names and calls it; a consumer holding a graph calls it through `held_config(graph)` / `config_from_nodes(nodes)` in `graph/held_config.py`, which derives nothing itself and caches the result on the committed document's node, taking it again whenever a held document's text changes (REQ-d00299-B). The derivation MUST stay a function of documents alone: `get_config` runs before any graph exists, because reading the configuration is what tells the builder where to look, so a derivation needing a graph could never produce one. Do NOT merge configuration layers anywhere else.
**Fix Command** (`commands/fix_cmd.py`): Single-pass pipeline: build graph, detect dirty nodes, generate changelog entries, `render_save()`. Spacing canonicalization happens at parse/build time. `compute_hash_for_node()` lives in `graph/render.py`. Associate path checks and no-requirements checks are in `health.py`.
**Git-Based Change Detection**: The `changed` command uses git to detect uncommitted changes to spec files.
**Git Repository Root Auto-Detection**: The CLI auto-detects the git repository root and runs as if invoked from there. This means `elspais` works identically from any subdirectory. Use `-v` flag to see "Working from repository root: ...". If not in a git repo, continues silently (warns with `-v`). Implementation: `find_git_root()` in `config/__init__.py`.
**No Canonical Root**: Associate paths resolve from `repo_root` (git root or CWD). There is no special worktree handling. If working in a git worktree with relative associate paths, use absolute paths in `.elspais.local.toml`. The `find_canonical_root()` function exists but is not used by the main code paths.
**Coverage Source Tracking**: `RollupMetrics` (`graph/metrics.py`) carries `total_assertions`, `assertion_coverage` (per-label `CoverageContribution` lists), and the dimensions `implemented`, `tested`, `verified`, `uat_coverage`, `uat_verified`, `code_tested`, `lcov_tested`. Each dimension is a `CoverageDimension` carrying the four per-label measure maps of REQ-d00069-L (fractional) and the per-_Assertion_ total taken from them. Where a contribution came from is a `CoverageSource` on the contribution inside `assertion_coverage` — DIRECT/EXPLICIT/INFERRED are values of that enum, not fields on `RollupMetrics`.
**Coverage Measures & Vocabulary Contract** (REQ-d00069-L/M/N, REQ-d00258): coverage is measured FOUR ways on two independent axes — what a citation named (**direct**, this _Assertion_ by name, vs **indirect**, the requirement as a whole) x where the evidence sits (**immediate**, attached here, vs **rolled**, conducted up a `Refines:` chain). They live on `CoverageDimension` as `immediate_direct_by_label` / `immediate_indirect_by_label` / `rolled_direct_by_label` / `rolled_indirect_by_label`; each is measured from the evidence itself rather than derived from a sibling (REQ-d00069-L). `total` and `immediate` are derived VIEWS over them, not further measures. The **total** (`total_by_label` / `covered`) is taken PER ASSERTION as the greatest of its four, so an _Assertion_ covered three ways is one covered _Assertion_ and `covered` never exceeds `total`. The retired strict/generous footings (`direct`/`indirect`), the `~` marker and the `[rules.coverage] allow_indirect` setting are GONE — do not reintroduce a caveat standing in for a measure a surface did not show (REQ-d00258-J). Reporting surfaces (CLI `summary`/`trace`, MCP `get_project_summary`, viewer) headline the total and publish the four measures beside it (REQ-d00258-A); work-list surfaces (`gaps`, health coverage checks, MCP `get_uncovered_assertions`/`get_test_coverage`) read the immediate direct measure alone (REQ-d00258-M). The one vocabulary is `MEASURE_WORDS` in `graph/aggregation.py` — "cited by name here" / "whole-requirement" / "conducted direct" / "conducted indirect" — and every surface renders through it. The coverage dimensions are defined one per assertion in **REQ-d00277**, so one can be added, redefined or withdrawn without rewriting a list; `COVERAGE_DIMENSIONS` in `graph/aggregation.py` names the set once. Their display words — **Implemented / Tested / Passing / UAT Covered / UAT Passed** — are the DEFAULTS of a per-relationship mapping a project may override (`[rules.coverage] status_words`, REQ-d00258-K), not the definitions. Avoid "Validated": it collides with the `Validates:` keyword. `Passing` counts an assertion only when a test declared against THAT assertion returned a passing result and none returned a failure (`tested_and_passing()` in `graph/metrics.py`, REQ-d00277-C). `Tested` is reported with a breakdown into passed / failed / awaiting a result accounting for every tested assertion (REQ-d00258-U, `tested_partition()`); the breakdown is not a display term of its own (REQ-d00258-V). **Line coverage is not a coverage dimension**: `code_tested` is a `LineCoverage` (`total_lines` / `attributed_lines` / `covered_lines`, plus the `has_measurement` and `has_contexts` bits recorded at ingestion) measured in LINES, aggregated by `aggregate_line_coverage()`, and never folded into the assertion measures (REQ-d00254-B). Those two bits are what tells an unasked question from a zero answer: with no coverage ingested a surface says so rather than printing `0/N`, and the attribution figure is suppressed only where the tooling recorded no per-test contexts (`has_attribution` reads `has_contexts`, REQ-d00258-W) — never merely because the count came out zero. `lcov_tested` IS assertion-shaped — line-coverage-derived credit keyed by assertion label — and carries the immediate measures only, because nothing conducts it. Every surface reporting a coverage figure or reaching a coverage verdict now derives it from this one aggregation (REQ-d00258-C, which names the property rather than a list of surfaces — an enumeration is how `get_subtree` and the viewer's per-assertion maps stayed conformant while computing their own). `get_subtree` reports every dimension of REQ-d00277 in its own right through `_compute_coverage_summary`, and the viewer's `/api/{test,uat,code}-coverage` maps report theirs through `_dimension_figures`; both headline the per-_Assertion_ total and publish the four measures beside it. A coverage count is a REAL number, not an integer — a journey verified in part credits in proportion (REQ-d00069-M). The word `covered` never stands for a union of dimensions: Implemented and Tested answer different questions and are always named.
**Multi-Assertion Syntax**: `Implements: REQ-p00001-A+B+C` expands to individual assertion references (`REQ-p00001-A`, `REQ-p00001-B`, `REQ-p00001-C`). Same for `Refines:`. The separator (`+` by default) is configured via `multi_separator` in `[id-patterns.assertions]`.
**Satisfies Relationship**: `Satisfies:` metadata declares compliance with a template requirement (e.g., a cross-cutting PRD). When a requirement declares `Satisfies: X`, the graph builder clones the template's REQ subtree with composite IDs (`declaring_id::original_id`), creating INSTANCE nodes. A `Stereotype` enum (`CONCRETE`, `TEMPLATE`, `INSTANCE`) classifies nodes, and `EdgeKind.INSTANCE` connects each clone to its original. Coverage uses the standard mechanism on cloned nodes. CODE citing a template _Assertion_ with `Implements:` and TEST citing one with `Verifies:` land a direct IMPLEMENTS or VERIFIES edge on the template _Assertion_ itself (REQ-p00014-D), and that evidence counts on every instance of it through the INSTANCE edge (REQ-p00014-P) — composite ids are not authoring syntax, so nothing redirects a citation to a clone. A hash change on any member of a template subtree flags the requirements whose `Satisfies:` cloned it for review. A subtree may span repositories (a template refining an associate's template joins its subtree), and each clone records the repository owning its own original in `template_repo`. The validation matrix's `Refines:`/`Implements:`/`Verifies:` rows have ONE authority, `stereotype_matrix_fault()` in `graph/template_subtree.py`, read by the builder and by the federation's cross-graph wiring alike before an edge is created, so a foreign target is judged by the rule a local one meets; the two `Satisfies:` rows (a target not marked **Template**, an INSTANCE target) are judged where a `Satisfies:` is instantiated, because there a refusal withholds a clone rather than an edge. DEFINES edges connect the declaring requirement's FILE node to each INSTANCE node (virtual provenance). INSTANCE nodes have no CONTAINS edges. `file_node()` returns None for INSTANCE nodes; navigate via INSTANCE edge to the original node to find the source file.
**Integrates (top-down external references)**: `Integrates:` is a consumer-side requirement keyword (spec files only) declaring that a requirement's implementation is provided by a requirement in a configured associate repo. Stored as `integrates_refs` on the REQUIREMENT node, rendered from that field (not derived from edges). A federation pass `FederatedGraph._wire_integrates_edges()` resolves the target in the owning associate and wires a dedicated `EdgeKind.INTEGRATES` edge (consumer REQ → library REQ) — distinct from IMPLEMENTS so the library's `Implements:` render never leaks the consumer ID, but coverage-contributing so the consumer counts as implemented. External-only (same-repo target → broken reference). Unresolved targets split hard (associate claims the ID format but lacks the ID) vs soft (`presumed_foreign`, non-failing). The consumer inherits the library requirement's implemented/passing coverage (`tested_and_passing()`) plus a `has_failures` flag via the live-query overlay `integrates_rollup()` (mirrors `satisfier_rollup`), surfaced in MCP/GUI.
**Associated Spec Scanning**: Multi-repo federation is configured via `[associates.<name>]` sections in `.elspais.toml`, each with `path` and `namespace` fields. The legacy `sponsors.yml`/`sponsors.local.yml` YAML system has been removed. Use `build_graph()` which automatically builds per-repo TraceGraphs when `[associates]` config is present.
**Optional Dependencies**: Advanced features are available via pip extras:

- `elspais[trace-view]`: HTML generation with Jinja2
- `elspais[trace-review]`: Starlette-based review server
- `elspais[all]`: All optional features
- Missing dependencies produce clear installation instructions.
**NodeKind.FILE**: Represents a source file as a first-class graph node. ID format: `file:<namespace>:<repo-relative-path>` — the namespace is the owning repository's, so two federation members holding the same repo-relative path own distinct nodes. Same shape for `rem:` and `def:` (which add `:<line>`), and for `result:`, whose last part is the record's ORDINAL among the records read from that place rather than a line — the place being the results artifact, or the target name where a runner's output held the results and no artifact exists (REQ-d00294-A+B). Build one ONLY through `make_file_id`/`make_remainder_id`/`make_definition_id`/`make_result_id` (namespace is a required first argument and an empty one raises), and take one apart ONLY through `parse_structural_id()` — all in `graph/GraphNode.py`. A reporter NEVER spells a result id: it numbers its records and the factory spells the id, because only the factory knows the repo root that makes the place repo-relative. A surface accepting a file reference from a caller (viewer routes, MCP tools) resolves a bare path through `file_id_for_reference()` in `utilities/spec_paths.py`, which reads it in the serving repository's namespace. `code:`/`test:` ids carry an absolute path and are not namespaced. Content fields include `file_type` (FileType enum), `absolute_path`, `relative_path`, `repo`, `git_branch`, `git_commit`.
**FileType Enum**: Classifies source files by domain role: `SPEC`, `JOURNEY`, `CODE`, `TEST`, `RESULT`, `CONFIG`. Lives in `graph/GraphNode.py` alongside `NodeKind`. `CONFIG` is the one member that names no parser: a configuration document produces no content nodes and is held because it was read (REQ-d00299-A). `build_graph` creates a node for `.elspais.toml`, and for `.elspais.local.toml` where one exists, before any spec file is read, carrying the parsed `TOMLDocument` in the `config_document` field. Which documents were read for a repository is answered ONCE, by `config_document_paths()` in `config/__init__.py`, which `load_config` reads too -- do NOT re-derive the overlay's path.
**NodeKind.DECLARATION**: One named entry a project declares in a configuration table -- today a `[scopes.NAME]`, and the kind is deliberately NOT named after scopes because the family grows as soon as another table gains coherent mutations. The table a node declares in is recorded on the node (`declares_table`), beside `declared_name` and the tomlkit item itself (`declaration`). ID format: `decl:<namespace>:<repo-relative-path>:<table>:<name>` -- the document is named because both the committed file and the machine-local overlay may declare the same name, and the id is DELIBERATELY not a structural id (its last part is a name, not a line), so `parse_structural_id()` does not admit it. Build, read and address one ONLY through `graph/declarations.py` (`build_declaration_nodes`, `declaration_text`, `declared_settings`, `iter_declarations`, `find_declaration`, and `DECLARED_TABLES`, which is the one place the set of held tables is named). `find_declaration` matches without regard to case and returns the declaration the derived configuration resolves to, the overlay's where both documents declare the name. These nodes hang from their CONFIG FILE node by CONTAINS edges carrying NO `render_order`: for a spec file the CONTAINS children in render order ARE the file's text, and for a configuration document they are not -- the document is the text, `CONFIG`'s renderer dumps it, and these children exist for addressing and versioning alone. `render_node()` on one is refused naming the document to render instead. `node_version()` gains a branch deriving a declaration's version from its own text and name and from nothing a neighbour holds, so two editors of two scopes do not collide; it stays the one authority (REQ-d00131-L, REQ-d00299-D).

**NodeKind.REMAINDER**: Unclaimed file content (not requirements).
**File Path Access Pattern**: File paths are accessed via `node.file_node().get_field("relative_path")`. Line numbers via `node.get_field("parse_line")`. The `SourceLocation` class and `GraphNode.source` field have been removed. `file_node()` returns None for INSTANCE nodes and unlinked nodes -- always check for None.
**FILE Node Build Pipeline**: `factory.py` creates FILE nodes (`file:<namespace>:<repo-relative-path>`) for every scanned file before parsing. `GraphBuilder` receives FILE nodes and wires CONTAINS edges to top-level content nodes (REQUIREMENT, USER_JOURNEY, CODE, TEST, file-level REMAINDER). CONTAINS edge metadata: `start_line`, `end_line`, `render_order` (float, sequential from 0.0). ASSERTIONs and requirement-level REMAINDER sections are reached via STRUCTURES from their parent REQUIREMENT, not CONTAINS from FILE. RemainderParser is mandatory for SPEC/JOURNEY/CODE/TEST files but NOT for RESULT files. `git_branch` and `git_commit` are captured once per repo.
**File-Based Documentation** (`elspais docs [topic]`): User documentation loaded from `src/elspais/docs/cli/*.md` files:
- **Single Source of Truth**: Markdown files in `src/elspais/docs/cli/` are the canonical docs. They ship inside the package, so the same files answer `elspais docs` from a wheel and from a checkout; there is no second copy at the repository root.
**PDF Reference Resolution** (`pdf/assembler.py`): `MarkdownAssembler.resource_roots()` is the ONE definition of the directories a relative image/`.mmd` reference may resolve against (each federated repo's root and its `spec/`); `pdf_cmd` passes that same set to pandoc as `--resource-path`. References the assembler cannot place are recorded as `AssemblyDiagnostic` entries (`iter_diagnostics()`) that `pdf_cmd` prints to stderr and summarizes in an `INCOMPLETE:` completion line — exit code stays 0; a spec file that cannot be found in its owning repository is recorded through the same diagnostics rather than dropping its requirements silently (a configured associate that cannot be read stops the build outright, so the assembler never meets one), and resources pandoc itself reports it could not fetch are folded into the same `INCOMPLETE:` count, deduplicated against the assembler's own findings.
**Edge Kind Classification** (`graph/builder.py`): `_STRUCTURAL_EDGE_KINDS` (CONTAINS, STRUCTURES) represent physical file structure; `_TRACEABILITY_EDGE_KINDS` (IMPLEMENTS, REFINES, SATISFIES, INTEGRATES, VERIFIES, VALIDATES, INSTANCE, DEFINES) represent requirement traceability. IMPLEMENTS: code → assertion (direct satisfaction). REFINES: requirement → requirement/assertion only (adds detail, splits assertions; cumulative; NOT valid in code/test files). REFINES adds no coverage by itself but is a coverage _conduction path_: a second annotator pass (`_conduct_refines_coverage`) propagates each refining requirement's own per-dimension coverage up to the targeted parent _Assertion_, equal-weight per incoming edge (REQ-d00069-J). Conduction writes the two ROLLED measures and nothing else: a citation's shape decides WHICH assertions receive a conducted value — the one `Refines: P/A` names, or every assertion where `Refines: P` names only the requirement — but NOT which measure it lands in, so a blanket citation still conducts the refining requirement's direct coverage into the parent's rolled DIRECT measure (REQ-d00069-J/L). Both conduct at full weight, equal-weight per incoming edge; the prior `1/N` blanket deflation is retired. Per-assertion coverage is therefore fractional and each measure is a sum of those fractions. Coverage _surfaces_ (MCP `get_test_coverage`, `get_uncovered_assertions`, `gaps`) treat an assertion as covered only at ~100% **and read the immediate direct measure** (REQ-d00258-M), so an assertion with no evidence naming it is a gap however much whole-requirement evidence its requirement carries and however finished the requirements refining it are; partial coverage stays a gap. Reporting surfaces (trace, summary, MCP project summary, viewer) headline the per-_Assertion_ total per REQ-d00258-A — the measures answer different questions. VERIFIES: produces pass/fail output (test → assertion, or code that generates results). VALIDATES: JNY → REQ/assertion (UAT coverage). These arrows are the DECLARATION direction — who writes the keyword, and about what. Storage inverts all of them uniformly: an edge is built as `target.link(source)`, so the CITED node is the edge's `source` and the CITING node is its `target` (a journey's `Validates:` yields an edge whose source is the requirement). To reach the journeys citing a requirement, walk that requirement's OUTGOING VALIDATES edges. Keyword validity: test files accept only `Verifies`; code files accept `Implements` and `Verifies`; spec files accept `Implements`, `Refines`, `Satisfies`, and `Integrates`; journey files accept `Validates` — and only in a journey's metadata, where it applies to the journey as a whole (REQ-p00014-V). A `Validates:` inside a journey section is NOT read; it is reported as a declared reference that produced no relationship. Step-scoped validation is deliberately unbuilt, so admitting the syntax would accept a distinction nothing computes. Used by reachability queries (`is_reachable_to_requirement()`) and health checks to distinguish structural orphans from unlinked nodes.
**Unified Traceability Graph**: a unified DAG structure representing the full traceability graph. `GraphNode` supports multiple parents (DAG), typed content (requirement, assertion, code, test, result, journey), and mutable metrics for accumulation. `TraceGraphBuilder` constructs graphs from requirements with automatic hierarchy linking.

**Iterator-Only Graph API**: The graph uses an iterator-only API to prevent accidental list materialization:

Use `walk(edge_kinds=...)` and `ancestors(edge_kinds=...)` for filtered recursive traversal. Use `child_count()`, `parent_count()`, `has_child()`, `has_parent()`, `is_root`, `is_leaf` for checks. Use `get_field()`, `set_field()`, `get_metric()`, `set_metric()` for content/metrics. Convenience properties: `level`, `status`, `hash`. Use `set_id()` for ID mutations. Use `file_node()` to find nearest FILE ancestor (returns None if not found). Use `link(child, EdgeKind)` for all relationships and `unlink(child)` to sever. **DO NOT** use `add_child()` or `remove_child()` -- they no longer exist.
  - **TraceGraph**: Use `iter_roots()` for traversal (accepts optional `NodeKind` filter: `iter_roots(NodeKind.FILE)` for FILE nodes, `iter_roots(NodeKind.REQUIREMENT)` for REQ roots only; default returns REQ+JOURNEY roots excluding FILE). Use `iter_by_kind(kind)` for general kind-based index queries. Use `root_count()`, `has_root()` for checks. Internal storage uses `_roots`, `_index` prefixed attributes. Use `is_reachable_to_requirement(node)` to check if a node can reach a REQUIREMENT ancestor via traceability edges. Use `iter_unlinked(kind?)` to iterate CODE/TEST nodes not linked to any requirement. Use `iter_structural_orphans()` to iterate nodes without a FILE ancestor.
  - **UUID for GUI**: Each node has a stable `uuid` (32-char hex) for DOM IDs and API endpoints.
**Graph Analysis** (`graph/analysis.py`): Read-only analytical functions that rank requirements by foundational importance. Computes PageRank centrality, fan-in branch count, and uncovered dependents. Does not modify the graph.
**Render Protocol & Save** (`graph/render.py`): Each NodeKind has a `render_node()` function that produces its text representation. `render_file()` produces a file's content through the renderer its file type declares, looked up in `FILE_RENDERERS` — the ONE authority for that question, so a renderer named anywhere else is the duplicate this project forbids. `SPEC`, `JOURNEY`, `CODE` and `TEST` declare the composed walk, which sorts the FILE node's CONTAINS children by `render_order` and concatenates their output. `CONFIG` declares a renderer that dumps the `TOMLDocument` the node holds, which is why an author's comments and spacing survive a round trip. `RESULT` declares none, so it is read-only and a request for its content is refused naming the type (REQ-d00131-I/Q). A walk over FILE nodes acts only on the file types it names (REQ-d00131-R), which is what lets a type be added without touching every caller. That file-type refusal is distinct from the `NodeKind.RESULT` refusal in `render_node()`: one is about the results artifact, the other about a record inside it. REQUIREMENT renders full block (header, metadata, body, assertions, sections, `*End*` marker with hash). REMAINDER renders raw text verbatim. USER_JOURNEY renders stored body. CODE/TEST render stored `raw_text`. ASSERTION and RESULT raise `ValueError` (rendered by parent or read-only). Requirement hashes are computed by `compute_hash_for_node()` (render.py), which dispatches on `hash_mode`: `normalized-text` delegates to `compute_normalized_hash()` in `utilities/hasher.py`, `full-text` to `calculate_hash()`. Per REQ-d00131-J, `compute_normalized_hash()` is order-independent: each normalized assertion is hashed individually, the per-assertion hashes are sorted lexicographically, and the sorted collection is hashed into the final result — assertion reorder does NOT change the hash. There is no `compute_requirement_hash()` function. `render_save()` persists dirty FILE nodes to disk — it identifies files with pending mutations, renders their content, and writes to disk. Implements/Refines references are derived from live graph edges. Supports optional consistency check (rebuild + compare) via `consistency_check=True` with a `rebuild_fn` callback. `persistence.py` is deleted; all save operations use `render_save()`.
**Node Mutation API**: TraceGraph provides mutation methods with full undo support
**Assertion Mutation API**: TraceGraph provides assertion-specific mutations

**File Mutation API**: TraceGraph provides file-level mutations: `move_node_to_file(node_id, target_file_id)` (re-wires CONTAINS edge), `rename_file(file_id, new_relative_path)` (updates ID, index, paths; render_save handles disk rename). Both support full undo.
**Optimistic Concurrency**: every graph node has a content-derived `version` token — derivation lives ONLY in `node_version()` (`graph/render.py`); ASSERTION/REMAINDER resolve to their owning REQUIREMENT's version. Every MCP `mutate_*` tool requires `if_version` and returns the new `version` on success; a stale token is rejected as `version_conflict` carrying `current_version` + `current_state`, a missing node as `node_not_found`. History-level tools require the mutation-log tip: `undo_last_mutation(if_mutation_id)`, `undo_to_mutation(mutation_id, if_tip_mutation_id)`, `save_mutations(if_tip_mutation_id)`, `refresh_graph(force=True, if_tip_mutation_id=...)`; `""` means "nothing pending"; a mismatch is `mutation_log_conflict` with `unseen`. Edge mutations guard the source; creation guards the parent (`mutate_add_requirement` unguarded without `parent_id`); `mutate_move_node_to_file` takes three tokens; `mutate_rename_file`/`apply_link` guard the FILE. MCP and the viewer's HTTP `/api/mutate/*` routes are at parity: routes delegate to the same `_guard_version`/`_guard_mutation_tip` helpers and return HTTP 409 with a body identical to the MCP rejection. ONE live graph per server process: `SharedServerState` (`mcp/shared_state.py`) is the single holder both surfaces dereference (MCP `_state` IS AppState's holder — do NOT cache the graph object across calls), and its `write_lock` serializes every guard+mutate and rebuild+swap (`@_locked` on MCP write tools, `@_serialized_write` on HTTP write routes — never await while holding it). `get_mutation_log()` returns newest-first and carries `current_tip` + `total`; snapshots come from `MutationLog.tail()`, never a live iterator. `build_time` lives in the holder too, so an MCP-side rebuild keeps the viewer's staleness check honest. In-memory mutations touch no file, so mtime staleness cannot see them: `freshness_report()` (`server/routes_api.py`) is the ONE computation behind `/api/check-freshness` and every event on `GET /api/events`, and carries `mutation_tip`. The page holds `/api/events` — a server-sent-events stream (`hello` on connect with the tip and the heartbeat interval, `change` within a 1s wake of `MutationLog.revision` or `build_time` moving, `heartbeat` at `_ELSPAIS_EVENTS_HEARTBEAT` seconds, default 30) — for the life of the tab through an `EventSource`; there is no 30s poll. The generator never takes `write_lock` and ends on `is_shutting_down`, so a held tab cannot stall a drain. Every event runs `applyServerEvent()`: `refreshDirtyCount({ adoptTip: false })`, then the stale/other-writer banner from the payload, comparing the announced tip against the last tip the page saw (re-read memory; do NOT reload from disk, which discards that writer's pending work). The viewer's unsaved badge is server-truth and tri-state — 0 hidden / N red / `?` amber when the server can't be asked (`editState.mutationCount` is `number | null`; never zeroed, never frozen at a stale count), and the stream is its heartbeat: silence for twice the announced interval, or a lost stream (the page closes the `EventSource` and retries at the interval itself, rather than letting the browser retry every few seconds and toast each failure), still runs the count probe so a dead server presents as `?`; the `beforeunload` warning arms only on a server-reported count > 0, read from state, not from badge text. That arming decision is inspectable rather than inferred: `window.unloadWarningState()` (edit mode only) reports the count, whether it is known, when and from where it was established, and the resulting `willWarnOnClose`, and the handler logs its decision to the console at navigation time — it reports, it never decides. Only `/api/dirty` may speak for the count (a stream failure must not touch it) and the probe never adopts the tip (doing so would retire the other-writer banner) — so an idle tab reflects another writer's pending mutations within about a second. Because an announcement can outrun the page's own bookkeeping, `apiFetch` tracks the page's own writes (`ownWriteRecently()`) and `noteAnnouncedTip()` defers the judgement by `OWN_WRITE_SETTLE_MS` while one is in flight or just finished; the page holds ONE pending judgement (`_tipJudgement`), replaced by every announcement, and at fire time it compares `editState.lastAnnouncedTip` — the tip last announced, not one captured when the deferral began — against `lastSeenTip`, so the page's own edits are never reported back to it as another writer's. Under an unknown count, branch-switch and checkpoint refuse with an error modal (REQ-d00267-E) — the opposite polarity from the navigation warning, which stays permissive because closing a tab destroys nothing. Agent-facing docs: `src/elspais/docs/cli/concurrency.md` (topic `concurrency`), `faq("concurrency")`, and `agent_instructions()`'s built-in `concurrency_protocol` section.
**Daemon Client Identity & Lifetime** (REQ-o00074): a daemon auto-started on behalf of a session is handed that session's PID at spawn time (`_ELSPAIS_CLIENT_PID` in the child env) because `start_new_session=True` detaches it and the parent chain is unrecoverable afterwards; it lands in `.elspais/daemon.json` as `client_pid`. Resolution lives ONLY in `resolve_client_pid()` (`mcp/daemon.py`) — `ELSPAIS_CLIENT_PID` (decisive, an unusable value yields None, no fallthrough; the name it was once written under, `ELSPAIS_SPAWNER_PID`, is NOT read, and a session setting only that one is told so once on stderr) > nearest `claude` ancestor under `CLAUDECODE` > controlling-terminal session leader with a tty > None. Explicit starts (`elspais daemon restart`, manual `mcp serve`, the viewer) pass no client and keep TTL-only lifetime — except `elspais viewer --session-lifetime` (REQ-o00079), which builds a `ClientWatchdog` with `client_pid=None` (an empty client set, NOT a watchdog that never fires) whose only liveness source is the tracker, so it persists and stops once no tab has held `/api/events` for the grace interval, counted from its start so the window before the first tab connects is the same window as any other — with or without pending changes, because a stream drops on a reload or a sleeping machine and comes back, where a dead pid does not (`shutdown_decision`'s `transient_handles`, derived from `client_pid is None`; the pid-daemon path still exits clean at the first check); its `exit_fn` unlinks `daemon.json` because `os._exit` skips the viewer's cleanup. ONE wiring for both processes: `build_client_watchdog()` in `server/client_watch.py` (pending snapshot from the holder's live graph, `finalize_shutdown` as `stop_fn`, tracker as `extra_liveness_fn`, `record_daemon_clients` as `publish_fn`, `_ELSPAIS_CLIENT_CHECK_INTERVAL`/`_ELSPAIS_CLIENT_GRACE` knobs, published as `shared["watchdog"]`) — do NOT hand-wire a second one. `ClientWatchdog` (`server/client_watch.py`) tracks a SET of client PIDs, not just the one that spawned the daemon: `ensure_daemon`'s reuse path POSTs `/api/session/attach`, which calls `attach_client()`, and the watchdog's own periodic check (`_publish`) republishes the client set into `daemon.json` as a typed `clients` list (`{"kind": "pid", "id": N}` entries plus a `{"kind": "session", "count": N}` entry when streams are held) whenever the composition changes, not only on attach; there is no `client_pids` key, and readers treat an absent `clients` key as "not recorded". A pid is not the only handle: ONE `HeldSessionTracker` (`server/session_track.py`), created in `create_app()` before either mount, wraps both the `/mcp` mount and the `/api/events` route (its `asgi()` returns an object, because a Starlette `Route` treats a function endpoint as a request handler) and counts GET streams still open, and the watchdog reads it through `extra_liveness_fn` — a client that supplies no pid is watched through the connection it holds, a request that COMPLETED is traffic and never counts (REQ-o00074-F), and a liveness source that raises keeps the daemon rather than reading as "no clients". When no handle can be derived, or a declared `ELSPAIS_CLIENT_PID` names a pid that is already dead, `notify_unbound_lifetime()` (`mcp/daemon.py`, REQ-o00074-N) prints a `note:` to stderr once per daemon (a `.elspais/daemon.client-notice` marker suppresses repeats) naming `ELSPAIS_CLIENT_PID` as the variable to set — a disclosure, never a refusal (REQ-o00075-G forbids making the daemon a dependency). The daemon KEEPs while any recorded client is alive and reaps itself independently of `cli_ttl` when none is. On expiry with pending work it AUTO-SAVES rather than discarding (60s interval, 1800s grace, neither reset by request traffic): the one save path is `persist_pending()` (`mcp/shared_state.py`, `automatic=True`), which supplies its own changelog message and writes `.elspais/automatic-save.json` via `record_automatic_save()`. That record carries facts only — `saved_by`/`saved_at`/`mutation_count`/`files_written`/`trigger`, NO verdict about the work — and surfaces as `automatic_save` on `get_workspace_info`, `get_graph_status`, `/api/dirty` and `/api/check-freshness`; a client-requested save clears it (`clear_automatic_save()` from `persist_pending` and `/api/save`). A failed auto-save retains the mutations and retries (`Decision.SAVE_FAILED`); the daemon does not exit. A mutation applied after all clients were seen gone still restarts the grace clock (reads move `MutationLog.revision` not at all, so polling cannot hold an orphan open).
**Shutdown Refusal**: `SharedServerState.begin_shutdown()` / `is_shutting_down` is raised the instant the process commits to stopping — inside the watchdog's locked decision, in `TTLMiddleware._exit`, and in `run_server`'s `uvicorn.Server.handle_exit` override for external SIGTERM. `_guard_shutdown()` (`mcp/server.py`, third member of the guard family) is checked INSIDE `_locked` and `_serialized_write`, returning `server_shutting_down`; HTTP returns the identical body with 409 (REQ-o00062-O parity, which binds the two surfaces to refuse identically; that the refusal exists at all is REQ-p00083-G). A _Traceability_ keyword is read ONLY behind the marker of the file's own language (REQ-d00269-K): `--` introduces a reference in SQL and is arithmetic in Python. This narrows WHERE a reference may be written and NEVER what it may say — the identifier grammar is one set of rules in every context that accepts a reference (REQ-p00014-T), spec metadata lines included. There are no per-file reference overrides.

Block comment forms (`/* */`, `<!-- -->`) are deliberately absent from the set and carry NO citation (REQ-d00082-H) — do not add an assertion or doc claiming otherwise. A language whose only comment form is a block therefore has no reference form: `.css`, `.html`, `.xml`, `.svg` are associated with no pattern. Term scanning legitimately reads block comments for a DIFFERENT purpose (finding a _Defined Term_) and is unaffected.

An extension the map does not name has NO pattern, so a keyword in it is read nowhere — deliberately the restrictive answer, never a permissive default. `.m` (MATLAB `%` vs Objective-C `//`) and `.s` are excluded precisely because they cannot name one pattern. `.j2` is `jinja-like` whatever it renders to (`viewer.js.j2`, `page.css.j2`, `page.html.j2` all annotate with `{# ... #}`) — a template is ONE scannable file type, so it carries ONE pattern. It is associated with its OWN comment rather than its output's: `{# #}` is a comment in every Jinja template and is removed before the output exists, so a citation is readable in a template rendering to HTML or CSS — neither of which has a line comment — and no citation reaches the rendered page. Reading the suffix beneath `.j2` would instead give those templates no reference form at all.

`prescan._COMMENT_PREFIXES` is DELIBERATELY separate and wider. It answers "does this line keep the downward walk to the next declaration alive?" — a question about file layout — not "may a keyword bind here?". Narrowing it to the file's one pattern would stop the walk at a block comment and cost the citation below it its declaration.

`prescan.opens_a_declaration` answers the same layout question for the lines that are not comments: a decorator/annotation (`@`) and a class header stand between a citation and the function it was written above without ending the downward walk, and are passed over (REQ-d00254-D speaks of functions and never of classes, so a class is passed over rather than bound to — a citation above one reaches the first function inside it, or nothing). It is passed as `skippable=` at the two CODE call sites and DELIBERATELY at none of the three test prescans, where an unbound citation is already answered by `UnboundCitation` (REQ-d00274-G/H) rather than by mis-attribution.

## Workflow

- **ALWAYS** use a sub-agent to write tests (unless you are the sub-agent)
- **ALWAYS** update user-facing surfaces when adding/modifying CLI features: `src/elspais/docs/cli/*.md`, `docs/configuration.md`, `src/elspais/commands/init.py` templates, CLI help/epilog text, and shell completion
- **ALWAYS** find a requirement with elspais, NEVER by grepping the spec files. Use MCP `search()` / `scoped_search()` / `discover_requirements()`, or `elspais search` on the CLI — one scorer (`mcp/search.py`) backs all of them. They traverse the traceability graph and rank by field-weighted relevance; grep matches strings in whichever files you thought to look at, which is how a thematic near-miss gets mistaken for the right requirement. `discover_requirements()` additionally prunes ancestors superseded by more specific descendants, so it answers "which DEV/OPS requirement actually covers this" rather than handing back the PRD above it. To find the code already serving a requirement, read its edges (MCP `get_requirement`/`get_subtree`) rather than grepping for the ID. grep is for confirming a string in a file these have already pointed you at.
- The query grammar is the same everywhere: an AND of OR-groups, precedence parentheses > `OR` > implicit AND, plus `"phrases"`, `-exclusion` and `=exact`. **Do NOT shorten a query to make it match.** Put each CONCEPT in its own parenthesised group with its synonyms inside — `(coverage OR measure) (immediate OR rolled)` — which is what finds a requirement whose exact wording you do not know. A query returning nothing is usually the SCOPE, not the query: widen the OR-groups or drop `scope_id`, rather than discarding the terms that describe what you are looking for.

## Testing

**Test tiers** (configured in `pyproject.toml`):

- `pytest` — runs unit/integration tests only. This is the default while iterating, but NOT how work is verified before a commit — see **Verifying a commit** below. Budget ~5m with `--no-cov`; `addopts` carries `--cov=src/elspais --cov-context=test` by default, so a plain `pytest` run is slower still. This is not a quick tier — prefer `-k`/`-m` narrowing while iterating.
- `pytest -m e2e` — runs e2e subprocess tests only. CLI commands, MCP protocol, CI workflows. Budget ~10m with `--no-cov`, or ~12m once the `browser` extra is installed: 34 of the browser tier's 41 tests carry BOTH `@pytest.mark.browser` and `@pytest.mark.e2e`, so they join this tier as soon as `playwright` imports. Without the extra the whole module skips on `importorskip` and this tier is 34 tests smaller — the count moving is that, not a regression. **Run it with the venv on PATH**: `PATH="$PWD/.venv/bin:$PATH" .venv/bin/python -m pytest -m e2e --no-cov`. The `stub` test target in `tests/fixtures/e2e-standard/.elspais.toml` shells out to bare `python`, so without that PATH `test_run_tests_happy_path` fails with exit 127 — an artifact of the invocation, not a defect (deliberately not changed to `python3`: many Windows setups have `python` and no `python3`, and a TOML command string cannot use `sys.executable`). Beware that a piped invocation from a bare shell reports **exit 0** on `python: not found` — a false green. Some PDF tests skip unless `xelatex` is installed.
- `pytest -m "e2e or browser"` — runs all slow tests.
- `pytest -m stress` — concurrency stress battery (~10s at default scale): barrier-released writer threads race the daemon's MCP and HTTP surfaces and assert the guard invariants (one winner per version token / mutation-log tip, no lost updates across save). Lives in `tests/stress/`; scale up with `ELSPAIS_STRESS_SCALE=10` for a soak run. CI runs it only when concurrency-relevant paths change (see the `stress-test` job's path filter in `ci.yml`); run it locally whenever you touch `mcp/`, `server/`, or graph mutation/render code.
- `pytest -m ""` — runs everything (unit + e2e + browser + stress). Budget the sum of the tiers above, well past 15m. **Run before `git push`.**

**Verifying a commit**: the verification pass is the commit itself, run in the background. `.githooks/pre-commit` does lint, markdownlint, `elspais fix` and the unit tier with `--junitxml`, then commits — one run, roughly eight minutes, most of it the tier (`--cov-context=test`, single process). Stage every touched file first: the hook's cache keys on `git write-tree`, so an unstaged run certifies the wrong tree, and the hook refuses outright on unstaged `src/` or `tests/`. Do not run a tier beforehand to check — a bare `pytest` writes no `--junitxml`, so it leaves neither a cached verdict (the commit re-runs everything) nor the result records elspais ingests (coverage then reports assertions as "awaiting a result" and `elspais checks` lists `tests.results_stale`). Never run two pytest processes in one worktree, and never kill one: each writes a `.coverage.<host>.pid<N>.<suffix>` shard, and a shard abandoned without its schema makes the next run pass every test and then fail every teardown with `no such table: context`. After stopping any run, `rm -f .coverage.*` before starting another.

**Marking tests**: Use `@pytest.mark.e2e` on tests that spawn external processes (elspais CLI, claude CLI, act, MCP subprocess). Use `@pytest.mark.browser` on Playwright tests.
**Browser tier setup**: `make setup` installs the extra and fetches the browser binaries; `pip install -e ".[browser]"` plus `playwright install chromium` does the same by hand. The tier is slow; expect it to take a while. The extra is deliberately NOT in `all` — `all` is the user-facing feature set (`elspais[all]`), and playwright is a test dependency, so it is installed by name there and by the `browser-test` CI job. Asking for the marker without the extra is a `UsageError`, not a skip (`pytest_configure` in `tests/conftest.py`), because the module opens with `pytest.importorskip("playwright")` and a missing extra would otherwise leave `pytest -m browser` exiting 0 having run nothing, which is indistinguishable from a pass. What counts as asking is decided by `_selects_marker()`, which evaluates the marker expression the way pytest's own selection does — the default options carry `not browser`, and a substring test reads that as a request for the tier it deselects. CI runs the tier only when viewer-relevant paths change (see the `browser-test` job's path filter in `ci.yml`); run it locally when you touch `html/`, `server/`, or the viewer command.
**Claude Code caveat**: The `test_e2e_install_and_uninstall` test (claude MCP install) is auto-skipped inside Claude Code sessions (`CLAUDECODE=1`) because the claude CLI hijacks pytest's file descriptors.

### Test-Writing Conventions

**Prefer the canonical graph**: Use the `canonical_graph` session fixture for read-only assertions instead of building ad-hoc graphs with `build_graph()` or `make_requirement()`. Use `canonical_federated_graph` when you need the FederatedGraph (e.g., trace rendering). Only create custom graphs when testing features not in the hht-like fixture (invalid inputs, specific config variations).

**Use incremental classes for mutation tests**: Mark with `@pytest.mark.incremental`, use the `mutable_graph` fixture. Assert after each mutation step. The fixture undoes all mutations on teardown via the undo log — no disk I/O for reset.

**No tautology tests**: Don't assert constants, factory return values, or type-system guarantees. Tests must exercise behavior — if the test can't fail due to a code change, it's not testing anything.

**Parametrize variants, don't duplicate**: If testing the same behavior across formats/configs, use `@pytest.mark.parametrize` with the shared fixture. Don't write separate test methods for each format.

**E2E fixture structure**: E2E tests are organized into 6 shared fixture files (test_e2e_global, test_e2e_standard, test_e2e_fda_numeric, test_e2e_named_custom, test_e2e_jira_edge, test_e2e_associated) plus test_e2e_special for unique setups. Each fixture builds one project with a daemon, and tests run sequentially against it. When adding new e2e tests, add them to the appropriate fixture file rather than creating a new file with its own project setup. Config dimensions (ID patterns, assertion labels, hierarchy rules) are crossed efficiently across fixtures.

**E2E: reuse MCP servers**: The `mcp` fixture in `test_mcp_e2e.py` is module-scoped. Don't start a new server per test class unless the project config differs.

**E2E: choosing the right fixture file**: Match your test to an existing fixture by config needs:
- `test_e2e_global` — runs against REPO_ROOT (self-validation, CLI smoke tests, global MCP)
- `test_e2e_standard` — standard IDs (REQ-p/o/d), uppercase assertions, 3-tier hierarchy, testing+code enabled
- `test_e2e_fda_numeric` — FDA-style IDs (PRD-/OPS-/DEV-), numeric-0 assertions, custom statuses, require_rationale
- `test_e2e_named_custom` — named-component IDs, numeric-1 assertions, custom hierarchy, SHALL=false, comma separator
- `test_e2e_jira_edge` — Jira-style variable-length IDs, zero-padded assertions, status_roles, complex dirs
- `test_e2e_associated` — multi-repo with associates (standard core + FDA associate)
- `test_e2e_special` — tests needing truly unique setup (init, lifecycle from scratch, specific error states)

**E2E: ordering within a fixture**: Read-only tests go first (health, summary, trace, analysis). Mutation tests (fix, config set, edit) go after. MCP tests go last. If your test mutates disk, add it after existing mutations — later tests expect the mutated state.

**E2E: when to create a new fixture file**: Only if you need a config combination that conflicts with ALL existing fixtures. Before creating a new file, check if you can add your config option to an existing fixture without breaking its other tests.
